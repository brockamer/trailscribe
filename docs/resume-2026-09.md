### Why the first `!ping` got no reply — root cause (confirmed 2026-09-11)

A multi-agent pass tested six hypotheses and adversarially verified each survivor.

| #   | Hypothesis                                           | Verdict                                               |
| --- | ---------------------------------------------------- | ----------------------------------------------------- |
| H1  | New IMEI absent from `IMEI_ALLOWLIST`                | **SUPPORTED** — sufficient on its own. **Now fixed.** |
| H2  | Sent to the wrong address (`tx.trailscribe.net`)     | REFUTED — the address was correct                     |
| H3  | Deployed base URL carries a trailing `/api`          | INCONCLUSIVE — secret is unreadable; not blocking     |
| H4  | New device not provisioned in the Garmin IPC account | **INCONCLUSIVE — only the operator can check**        |
| H5  | Garmin merely held the reply (~75s)                  | REFUTED — explains delay, not total silence           |
| H6  | Production Worker not live                           | REFUTED — live, deploys on push to main               |

**H1 mechanism.** `src/app.ts:163` is the first statement of `handleEvent()`:

```ts
if (!event.imei || !allow.has(event.imei)) {
  log({ event: "imei_not_allowed", level: "warn", imei: event.imei });
  return;
}
```

It returns before the idempotency write, before dispatch, and before any of the seven
`sendReply` call sites. The route then answers `c.text("ok", 200)` unconditionally, so Garmin
sees success and never retries. The device receives nothing, and D9 (email fallback) is skipped
for α — so there is no second channel. **A stale IMEI is indistinguishable from a dead network
at the device.**

Corroborating evidence: production KV holds `ledger:2026-04` and `ledger:2026-05` but **no
`ledger:2026-09`** — no billable transaction was ever recorded for the new device.

**H2 is dead, and worth stating plainly** (issue #121): Garmin IPC Outbound forwards _every_
message from a Pro-tenant device to the webhook regardless of the chosen recipient. The `To:`
field is informational. `trailscribe@tx.trailscribe.net` is a convention, not a route.

**H4 is the remaining unknown.** If the replacement device was never added to the Garmin
Professional account, Garmin never calls the webhook at all — same silent symptom. Distinguish
the two with `pnpm exec wrangler tail --env production --format=json` while sending `!ping`:
an `imei_not_allowed` line means the allowlist; _no log line at all_ means Garmin never called.

### Latent gap found in passing

`parseEnv()` is never called on the request path — `src/app.ts` reads `c.env` directly. The zod
regex on `IMEI_ALLOWLIST` (`src/env.ts:116`) is therefore documentation, not a runtime gate; a
malformed secret would fail silently rather than loudly. Worth a small issue.
